# 路线图（阶段门禁）

每个阶段写明**目标、范围内、明确不做、出口标准**。出口标准达不到，就不开始下一阶段。"明确不做"清单里的需求记入 Issue（标注阶段），不要顺手实现。GitHub Milestones 和阶段一一对应。

## P0 · 骨架（已完成）

- 模块化单体，六个模块全部打通；最薄端到端链路（mock 引擎 → 快照 → 分析 → 指标 → 看板）
- 6 个 API 型引擎适配器、3 条审计规则
- 架构治理全部上线：import 合约、架构测试、契约与 golden 测试、CI、ADR 门禁、Claude Code hooks 和 skills

## P1 · MVP 自用（0–3 月）

**目标**：团队自己每天用它监测品牌在国内外 AI 引擎里的表现，并据此改进内容。

**范围内**
- 采集：
  - 定时运行（Celery Beat 加 `schedules` 表）
  - 按引擎令牌桶限流，失败重试策略
  - SERP 型适配器：Google AI Overviews、百度 AI 搜索
  - 带搜索工具的 API（OpenAI Responses + web_search 等），提高保真度
  - 补齐文心、腾讯元宝、Gemini
- 分析：
  - LLM 情感评判（小模型，结构化输出，带缓存）
  - 歧义品牌的 LLM 兜底
  - 列表型答案的位次识别
- 指标：时间序列看板（ECharts）、按引擎和主题切片、Prompt 分组（topic / prompt_set）
- 审计：多页面爬取（sitemap）、SSR 与 CSR 对比（Playwright）、结构化与 E-E-A-T 规则扩充到 15 条以上
- 运维：结构化日志、OpenTelemetry、Sentry；按引擎统计成功率、成本和延迟

**明确不做**：多租户与计费、登录体系（单租户部署、内网访问）、浏览器采集模式、ClickHouse、开放 API、告警。

**出口标准**
- 至少 6 个真实引擎在线，连续 30 天定时采集成功率 ≥98%
- 审计规则 ≥15 条，每条都有正例和反例
- 看板每周都在实际使用，至少一个内容优化决策是依据它做出的
- `make check` 常绿，`docs/tech-debt.md` 中没有过期未偿还的条目

## P2 · 平台化 SaaS（3–9 月）

**目标**：多个团队或客户自助使用，并能计费。

**范围内**
- 身份与租户：
  - 用户、成员、RBAC、API Key
  - Postgres RLS
  - 配额与计费（基于 `usage_ledger`）
- 采集：
  - 区域采集 Agent（拉模式）：国内和海外节点通过 HTTPS 从控制面领取任务、回传快照，避免跨境直连队列
  - 浏览器采集模式（需要先写合规 ADR）
- 数据：按演进触发器引入 ClickHouse；国内客户数据驻留国内
- 新模块（每个都要写 ADR）：
  - `alerts`：阈值告警，通知渠道包括邮件、飞书、企业微信、Slack
  - `reports`：报告导出（PDF / 白标）
  - `citations`：引用源情报，找出"AI 信任但你缺席"的来源
  - AI 爬虫访问日志分析：接入 Nginx / CDN 日志
- 内容优化建议：LLM 生成，结合审计结果和引用源

**明确不做**：开放平台、插件市场、服务拆分（除非触发器已触发）。

**出口标准**：≥3 个外部租户稳定使用 30 天；租户隔离渗透测试通过；计费对账误差 <1%。

## P3 · 开放平台（9 月+）

- Public API + Webhook + SDK；OpenAPI 版本化（`/v1`）
- 按扩缩特征拆分服务：先拆 collection（出口 IP、区域、并发特征不同），再拆 analysis（成本特征不同）
- 需要长流程时引入 Temporal
- Agency 白标与客户子账号
- 适配器和规则插件市场
